# AGENTS.md

Instructions for AI coding agents working in this repository.
Humans: see [README.md](README.md) and [CONTRIBUTING.md](CONTRIBUTING.md).

## Project

Terraform/OpenTofu provider for Scalr (`registry.scalr.io/scalr/scalr`). Go (version in
`.go-version`), Terraform Plugin Framework v1 and Plugin SDK v2 served together through
`tf5muxserver`. Product docs: <https://docs.scalr.io>

## Repository Map

- `main.go`: entry point, mux setup, and the `go:generate` directives for docs.
- `internal/provider/`: every resource, data source and acceptance test, in one package.
  - `provider.go`: Framework provider; registers Framework `Resources()` / `DataSources()`.
  - `provider_sdk.go`: SDK v2 provider; registers `ResourcesMap` / `DataSourcesMap`.
  - Framework files: `<name>_resource.go`, `<name>_data_source.go`, where `<name>` is the type
    name without `scalr_` (`scalr_var_set` → `var_set_resource.go`). Large resources may be split
    into `<name>_schemas.go`, `<name>_models.go`, `<name>_migrate.go` (see Code Conventions).
  - SDK v2 files (legacy): `resource_scalr_<name>.go`, `data_source_scalr_<name>.go`,
    `resource_scalr_<name>_migrate.go`. The old prefix marks what is still legacy.
  - Tests sit next to the code: `<file>_test.go`. Shared test helpers: `testing.go`,
    `provider_test.go` (`protoV5ProviderFactories`), `provider_sdk_test.go` (`testAccPreCheck`).
- `internal/framework/`: shared Framework code: `ResourceWithScalrClient` /
  `DataSourceWithScalrClient` base types, value helpers (`SetIfKnown*`,
  `FlattenRelationshipIDs*`, `ExpandRelationshipIDs*`), `defaults/`, `planmodifiers/`,
  `validation/`.
- `internal/client/`: API client configuration and mocks for unit tests.
- `examples/`: `.tf` snippets and `import.sh` files consumed by tfplugindocs.
- `templates/`: tfplugindocs templates; per-resource overrides in `templates/{resources,data-sources}/`.
- `docs/`: generated by `go generate`, published to readme.io. Never hand-edit.

## Architecture Invariants

1. New resources and data sources, including their tests, use only the Plugin Framework and
   go-scalr v2 (`github.com/scalr/go-scalr/v2`, `r.ClientV2`, `createScalrClientV2()` in tests).
   They must not import `github.com/hashicorp/terraform-plugin-sdk/v2/...` or go-scalr v1
   (`github.com/scalr/go-scalr`). Tests use `github.com/hashicorp/terraform-plugin-testing`.
   Enforced by the `depguard` rule in `.golangci.yml`; its exception list only shrinks. Remove a
   file from it when the file moves to v2; never add one.
   SDK v2 resources and Framework resources on go-scalr v1 are migrated gradually, usually as
   part of a task that touches them (see Agent Workflow § Legacy resources).
2. go-scalr v2 is generated from fatmouse `taco/openapi/openapi-public.yml` (`../go-scalr/v2`,
   `make generate`). An API missing from v2 is added there, never worked around with v1. v1
   (`r.Client`, `meta.(*scalr.Client)`) is hand-written and frozen. Many existing Framework
   resources and tests still use it: legacy, never a template for new code.
3. Never break existing state. A schema change that alters stored shape or meaning bumps the
   schema `Version` and adds a state upgrader with a test. A Framework resource that replaced an
   SDK one keeps the SDK schema version chain.
4. Generated artifacts, never hand-edited: `docs/**` (`go generate`), `go.sum` (`go mod tidy`).
   Run `go mod tidy` after every dependency change (`go get`, a go-scalr pin, dropping a
   `replace`), so `go.sum` keeps no stale entries next to the new versions.
   `go mod tidy -diff` must print nothing; CI (Lint job) fails otherwise.
   CI fails when `go generate` leaves a diff.
5. Every user-facing attribute and the resource itself carry a `MarkdownDescription`
   (`Description` in SDK v2). It is the documentation.
6. Changelog: every user-visible change gets an entry under `## [Unreleased]` in `CHANGELOG.md`.
   Use the [provider-changelog](.agents/skills/provider-changelog/SKILL.md) skill.

## Commands

```bash
make build                                   # build the provider binary
make install                                 # build and copy into ~/.terraform.d/plugins
make test                                    # unit tests; acceptance tests skip without TF_ACC
make vet
make fmt                                     # golangci-lint fmt: gofumpt + gci import groups
golangci-lint run                            # what CI runs (v2.6.1, config in .golangci.yml)
pre-commit run --files <changed files>       # all local hooks; `pre-commit install` once per clone
go generate                                  # terraform fmt examples + tfplugindocs + page order
go test ./internal/provider -run 'TestResourceScalrVcsProviderStateUpgradeV0' -v   # one unit test

# Selected acceptance tests against the test Scalr in .scalr-testenv.env
# (see provider-acceptance-tests skill first)
make testacc-one RUN='^TestAccScalrTag_basic$'

go get github.com/scalr/go-scalr/v2@<commit-sha> && go mod tidy   # pin go-scalr
```

`go generate` and the pre-commit `terraform fmt` hook need the `terraform` binary on `PATH`.
`golangci-lint` must be v2 (`go install github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.6.1`);
v1 cannot read `.golangci.yml`. Never run the full `make testacc` locally: it takes up to 45
minutes and creates real objects.

## Code Conventions

- Before writing non-trivial code, read one or two recent neighbours of the same kind and match
  them. Most neighbours are legacy; the Framework + v2 references are listed in
  [provider-new-resource § Start from a neighbour](.agents/skills/provider-new-resource/SKILL.md#start-from-a-neighbour).
- Schema and CRUD recipes (ID, `account_id`, secrets, validation, not-found, `null` vs `""`,
  `value.Unset` vs `value.Null`, errors) live in
  [provider-new-resource § Schema rules / CRUD rules](.agents/skills/provider-new-resource/SKILL.md#schema-rules)
  and apply to any Framework code you write, not only new resources.
- Splitting a resource into files is a judgement call, not a rule. Keep a simple resource in one
  `<name>_resource.go`. Split one that is large (several hundred lines), has prior schema versions
  and upgraders, or shares models with its data source:
  - `<name>_resource.go`: the resource type, `Configure`, CRUD, import, `UpgradeState` wiring,
    request building.
  - `<name>_schemas.go`: the current schema, frozen prior versions (`<name>ResourceSchemaV<N>`),
    validators and plan modifiers only this schema uses.
  - `<name>_models.go`: model structs and `<name>ResourceModelFromAPI`, shared with the data
    source where the shapes match.
  - `<name>_migrate.go`: state upgraders.

  Examples: `workspace_*`, `variable_*`, `storage_profile_*` (models shared with the data source).
  Splitting an existing resource is a refactor: do it on request or as part of a migration, not
  alongside an unrelated fix.
- File names: new and migrated resources and data sources use `<name>_resource.go` /
  `<name>_data_source.go` and the matching `_test.go`, never `resource_scalr_*` /
  `data_source_scalr_*`. A migration renames them
  ([provider-sdk-to-framework](.agents/skills/provider-sdk-to-framework/SKILL.md)).
- Before naming a new resource, data source or attribute, read
  [CONTRIBUTING.md § Naming conventions](CONTRIBUTING.md#naming-conventions) (type names, link
  resources, attributes, relationships). Released names never change.
- Formatting is gofumpt (extra rules) plus gci with import groups: standard library,
  third-party, `github.com/scalr/go-scalr...`, this module. `make fmt` applies both; never
  hand-format against them.
- Comments only for a non-obvious why.

## Testing

- Unit tests (`make test`): pure logic, state upgraders (`assertCorrectState` in `testing.go`),
  helpers. No network.
- Acceptance tests: `resource.Test` with `ProtoV5ProviderFactories: protoV5ProviderFactories(t)`
  and `PreCheck: func() { testAccPreCheck(t) }`. They run against a real Scalr built from
  fatmouse, so they depend on its seed data (`defaultAccount`, `testUser`, roles in `testing.go`).
- Bug fix ⇒ an acceptance step (or unit test) that fails without the fix. Regression tests are
  named `TestAcc<Resource>_SCALRCORE_<n>`.
- Details, CI behaviour and pitfalls:
  [provider-acceptance-tests](.agents/skills/provider-acceptance-tests/SKILL.md).

## Cross-repo Flow

- The branch name is the Jira key (`SCALRCORE-12345`). CI acceptance tests build a preview Scalr
  from the fatmouse branch with the same name, falling back to fatmouse `master`. A provider
  change that needs unreleased API work must have a same-named fatmouse branch.
- Checkouts are siblings: `../fatmouse` (owns the OpenAPI spec), `../go-scalr`, and this repo.
  If either sibling is missing, ask where it is; do not clone it yourself.
- API missing from go-scalr v2 (usually a new resource whose API landed recently): see
  [Regenerating go-scalr v2](#regenerating-go-scalr-v2).
- Scalr is SaaS only, so the provider does not track a minimum server version. A provider change
  that needs new server behaviour is released only after that fatmouse change is deployed.
- Releases: `release/X.Y.Z` branch, a changelog PR into it that turns `[Unreleased]` into
  `[X.Y.Z] - <date>`, then a `vX.Y.Z` tag (GoReleaser, `release.yml`; the tag also publishes
  `docs/` to readme.io). Every push to `release/**` is backported to `master` automatically
  (`misc-backport.yml`; on a conflict it opens a backport PR). Do not cherry-pick release
  changes into `master` by hand.

### Regenerating go-scalr v2

1. `../fatmouse` on the branch that has the API: the same Jira key branch while the server work
   is unreleased, otherwise an up-to-date `master`. Do not switch or pull branches in a sibling
   repo with uncommitted changes; ask first.
2. In `../go-scalr`, a branch named after the Jira key, then `cd v2 && make generate`. It reads
   `../../fatmouse/taco/openapi/openapi-public.yml` and rewrites the `*.gen.go` files.
3. Review the generated diff. Spec changes from other teams come along; that is expected. A
   missing or wrong operation for your API means the spec or the generator is at fault: fix the
   spec in fatmouse or the generator in `v2/internal/generator/`, never the `.gen.go` files.
   `make test` in `v2` covers the generator.
4. Iterate locally with `go mod edit -replace github.com/scalr/go-scalr/v2=../go-scalr/v2`.
   Remove the replace (`go mod edit -dropreplace github.com/scalr/go-scalr/v2`) and run
   `go mod tidy` before pushing.
5. Push the go-scalr branch, open its PR, and pin its head commit here:
   `go get github.com/scalr/go-scalr/v2@<branch-sha> && go mod tidy`. Pinning an unmerged
   go-scalr commit is the normal flow: the related PRs are merged together, with merge commits,
   so the pinned commit lands in go-scalr `master` unchanged. Re-pin after every push to the
   go-scalr branch.

## Boundaries

### Ask first

- Removing or renaming a resource, data source or attribute, or changing an attribute's type,
  `Required`/`Optional`/`Computed` mode, or `RequiresReplace` behaviour on an existing resource.
- Bumping a schema version / adding a state upgrader.
- Migrating a legacy resource: SDK v2 → Framework, or go-scalr v1 → v2 (see Agent Workflow §
  Legacy resources).
- New dependencies in `go.mod` (go-scalr bumps excepted).
- Changes to `.github/workflows/**`, `.goreleaser.yml`, release or signing setup.

### Never

- Hand-edit `docs/**`, or commit without re-running `go generate` after a schema, example or
  template change.
- Break state compatibility, or delete/skip a test to make CI pass.
- Run `make testacc` or acceptance tests against a production Scalr account.
- Commit secrets, tokens, `.scalr-testenv.env`, `gha-creds-*.json`, `covprofile`, or built
  binaries. Read or print `.scalr-testenv.env`; only `make testacc-one` uses it.
- Push to `master` or `release/**`, or force-push shared branches.

## Agent Workflow

- Smallest change that solves the ticket. No unrequested refactors, no speculative helpers.
  Migrating a legacy resource the task touches is the one refactor you offer (below).
- Touching 3+ resources, or a migration: propose a plan first.
- Pick the matching skill: new resource/data source → `provider-new-resource`; attribute
  add/change/deprecate/remove → `provider-schema-change`; SDK → Framework or v1 → v2 →
  `provider-sdk-to-framework`; bug → `provider-fix-issue`; review → `provider-code-review`.
- Before reporting done: `make build`, `make vet`, `pre-commit run --files <changed files>`
  (or `golangci-lint run` when pre-commit is unavailable), the relevant unit tests,
  `go generate` with a clean or intended diff, `go mod tidy -diff` empty when dependencies
  changed, and a changelog entry. State plainly which acceptance tests you did not run.

### Legacy resources

Legacy code is migrated gradually: SDK v2 resources to the Framework, and Framework resources
still on go-scalr v1 to v2. v1 will be removed entirely. Legacy files are the
`resource_scalr_*.go` / `data_source_scalr_*.go` ones and those in the depguard exception list in
`.golangci.yml`.

When a task changes a legacy resource or data source (including its test file), ask the
developer before writing code whether to migrate it as part of the task: SDK → Framework + v2,
or v1 → v2 for a Framework resource. Migrating is preferred, not required. Give a recommendation
with a reason:

- Keep it narrow: a small or urgent fix, or a port that is not straightforward: logic that does
  not fit the Framework (`CustomizeDiff`, `DiffSuppressFunc` with side effects, behaviour that
  would differ), or go-scalr v2 not covering the endpoint correctly. Suggest a separate migration
  ticket.
- Migrate: the task already reworks much of the resource, or the port is straightforward.

go-scalr v2 is generated, so a gap can be a generator bug, an unsupported spec construct, or a
spec newer than the generator. Check the pinned v2 for the operations and fields the resource
needs before recommending a migration. A gap is fixed in go-scalr (spec or generator), not
worked around with v1 in new code; until then the resource stays on v1.

On a yes, follow `provider-sdk-to-framework` and migrate first, with no behaviour change, in its
own commit; then make the task's change on the migrated version. Keeping the steps apart keeps
the upgrade test meaningful and the review readable. On a no, change the legacy code narrowly and do not mention the migration again.

## Writing Style

Prose (PR text, comments, changelog, descriptions) is engineer-to-engineer: short sentences,
plain words, what the thing does and its caveats. No inflated adjectives, filler, rule-of-three
padding, "X, not Y" slogans, bold for emphasis, or em dashes. Do not describe the session or the
tooling.

Start every AI-assisted GitHub comment posted from a human account with `<sub>🤖AI-assisted</sub>`
on its own line, followed by a blank line.

### Pull requests

- Title: the Jira key followed by the ticket summary, `SCALRCORE-<n> <Jira summary>`. With a
  ticket given, take the summary from Jira as is; without one, ask for the key.
- Body: the template in `.github/PULL_REQUEST_TEMPLATE.md` with honest checkboxes. Add prose
  above it only for what the diff does not show: root cause, a state or BC impact, the fatmouse
  companion branch/PR that must be deployed first. Under 150 words. No test-run reports.

### Commit messages

Subject ≤ 50 characters (72 hard limit), capitalized, imperative, no trailing period, blank line,
body wrapped at 72 explaining what and why.
